# Алгоритм подбора решений

## Назначение документа

Документ описывает логику подбора роботизированных решений под конкретный
объект: правила фильтрации, условия исключения, ранжирование, ручное
добавление и сравнение. Источником хранения результатов является
selection_result (docs/data_model.md §10.7).

## 1. Входные данные

- project — объект пользователя (склад, аэропорт, медицина).
- project_parameter_value — значения параметров объекта.
- object_type_parameter — метаданные параметров (единица, тип, обязательность).
- solution — каталог решений с 8 обязательными ТТХ (колонки).
- solution_characteristic — EAV-значения ТТХ (после дозаполнения из открытых источников).
- solution_application — применимость решений к отраслям и процессам.
- object_type_industry — маппинг «тип объекта → отрасли».

## 2. Шаг 1. Определение отраслей

Маппинг «тип объекта → отрасли» — из assumptions.md §1:

- Склад → trade_and_services, manufacturing, transport_and_logistics
- Аэропорт → transport_and_logistics, security
- Медучреждение → security, trade_and_services

Реализация: таблица object_type_industry (7 связей в seed).

SQL-логика:

    SELECT industry_id FROM object_type_industry
    WHERE object_type_id = :objectTypeId;

## 3. Шаг 2. Первичная фильтрация по отрасли

Из каталога выбираются решения, у которых есть solution_application для
отраслей объекта.

    SELECT DISTINCT s.* FROM solution s
    JOIN solution_application sa ON sa.solution_id = s.id
    JOIN object_type_industry oti ON oti.industry_id = sa.industry_id
    WHERE oti.object_type_id = :objectTypeId;

Результат: пул решений, применимых к типу объекта.

## 4. Шаг 3. Фильтрация по обязательным ТТХ

Сравниваем 8 обязательных ТТХ решения (колонки solution, assumptions.md §21)
с параметрами объекта. Источники параметров — object_type_parameter для типа
объекта; значения — project_parameter_value (если пользователь задал) или
базовые/диапазонные значения из object_type_parameter.

### 4.1. Таблица сравнения

| ТТХ решения               | Поле решения            | Параметр объекта           | Правило                                          | Источник worst-case                                              |
|---------------------------|-------------------------|----------------------------|--------------------------------------------------|------------------------------------------------------------------|
| Грузоподъёмность          | payload_kg              | Масса грузовой единицы     | payload_kg >= max_weight                         | MAX из диапазона массы грузовой единицы (не среднее)             |
| Собственная масса         | mass_kg                 | Нагрузка на пол            | mass_kg <= floor_load_max                        | MAX нагрузки на пол (если параметр задан; иначе — needs_check)   |
| Длина                     | length_mm               | Ширина рабочих проходов    | length_mm < min_passage_width                    | MIN из диапазона проходов                                        |
| Ширина                    | width_mm                | Ширина главных проездов    | width_mm < min_aisle_width                       | MIN из диапазона проездов                                        |
| Высота                    | height_mm               | Высота потолков / ярусов   | height_mm < min_ceiling_height                   | MIN из диапазона высот                                           |
| Точность позиционирования | positioning_accuracy_mm | Требование к точности      | positioning_accuracy_mm <= min_required_accuracy | Параметр объекта или допущение; иначе — needs_check              |
| Мощность зарядки          | charging_power_kw       | Доступная мощность зарядки | charging_power_kw <= available_charging_power    | Параметр объекта или доля от общей мощности; иначе — needs_check |
| Уровень шума              | noise_level_dba         | Допустимый уровень шума    | noise_level_dba <= max_allowed_noise             | MIN из диапазона допустимого шума                                |

Правило сравнения — строгое:
- < (строго меньше) для габаритов и высоты.
- <= (меньше или равно) для грузоподъёмности, точности, мощности, шума, массы.

Почему MAX для грузоподъёмности и MIN для остального:
- Грузоподъёмность робота — worst-case: если попадётся груз тяжелее среднего,
  робот должен его поднять. Поэтому сравнение с максимальной массой грузовой
  единицы из диапазона.
- Габариты, высота, шум — worst-case: если робот не пройдёт в самый узкий
  проход или не впишется под самый низкий ярус, решение неприменимо. Поэтому
  сравнение с минимальным значением из диапазона.

Единицы (assumptions.md §3): ТТХ решений — кг, мм, кВт, дБА. Параметры
объекта задаются в метрах (ширина проходов, проездов, коридоров, высота
потолков). Единственная конвертация — м → мм (× 1000) на границе сравнения
габаритов.

Данные из EAV: если ТТХ заполнено в solution_characteristic (после
дозаполнения из открытых источников), значение берётся оттуда; колонка
solution — материализованная проекция (data_model.md §2.1, §5.8).

#### Фактический маппинг «проверка → параметр объекта»

| Проверка                        | Склад                                    | Аэропорт                      | Медучреждение                 |
|---------------------------------|------------------------------------------|-------------------------------|-------------------------------|
| Грузоподъёмность vs масса груза | pallet_unit_weight (worst-case max)      | avg_baggage_weight            | meal_trolley_weight_gross     |
| Масса vs нагрузка на пол        | floor_load_max_kg                        | — нет параметра               | — нет параметра               |
| Длина vs рабочие проходы        | rack_aisle_width (м)                     | —                             | main_corridor_width (м)       |
| Ширина vs главные проезды       | main_aisle_width (м)                     | —                             | —                             |
| Высота vs потолки               | storage_zone_ceiling_height (м)          | —                             | —                             |
| Точность                        | required_positioning_accuracy_mm         | тот же                        | тот же                        |
| Мощность зарядки                | available_power_capacity                 | charging_infrastructure_power | charging_infrastructure_power |
| Шум                             | max_allowed_noise_dba                    | тот же                        | тот же                        |

«— нет параметра» — параметр для этого типа объекта не предусмотрен; по §5.2
все решения получают needs_check «параметр объекта не задан» (допущение
можно задать вручную значением параметра или добавить параметр
overrides-файлом). Коды — фактические; склад — полный набор из 8 проверок.

Эффективное значение параметра: строка project_parameter_value, иначе
дефолт object_type_parameter (worst-case — assumptions.md §25).

## 5. Шаг 4. Исключения и «требует проверки»

### 5.1. Критическое ограничение → excluded

Ключевое ограничение, делающее использование невозможным, — основание не
рекомендовать продукт.

Строгое сравнение: если хотя бы один обязательный ТТХ нарушен — решение
исключается. Никаких «с запасом», «примерно», «округлим».

Условия исключения:

| Условие                                         | Пример                                 |
|-------------------------------------------------|----------------------------------------|
| payload_kg < max_weight                         | Робот не поднимет паллету              |
| mass_kg > floor_load_max                        | Робот продавит пол                     |
| length_mm >= min_passage_width                  | Робот не проедет между стеллажами      |
| width_mm >= min_aisle_width                     | Робот не развернётся в главном проезде |
| height_mm >= min_ceiling_height                 | Робот не впишется по вертикали         |
| positioning_accuracy_mm > min_required_accuracy | Не выполнит операцию точно             |
| charging_power_kw > available_charging_power    | Негде заряжать                         |
| noise_level_dba > max_allowed_noise             | Нарушает нормы шума                    |

При нескольких нарушениях — все попадают в reason (для объяснимости).

### 5.2. Нехватка данных → needs_check

При недостатке данных решение помечается как требующее проверки.

Из assumptions.md §7: is_confirmed = false → needs_check.

Условия needs_check:

| Условие                                                                       | Что происходит                                |
|-------------------------------------------------------------------------------|-----------------------------------------------|
| ТТХ решения = NULL                                                            | Нет данных для сравнения                      |
| Часть обязательных ТТХ NULL                                                   | Нельзя оценить полностью                      |
| Параметр объекта не задан (NULL)                                              | Не с чем сравнивать                           |
| is_confirmed = false у ТТХ                                                    | Данные не подтверждены независимым источником |
| ТТХ из открытого источника без source_url                                     | Провенанс неполный                            |
| Параметр требует допущения (точность, нагрузка на пол), а допущение не задано | Нет эталона сравнения                         |

Правило: needs_check — не исключение, а флаг «нужна ручная проверка».
Решение остаётся в списке, пользователь видит список недостающих данных.

Приоритет проверки: сначала excluded (критические), потом needs_check,
оставшиеся — fit.

### 5.3. Полное соответствие → fit

Если все 8 обязательных ТТХ заполнены, не нарушены, is_confirmed = true или
заполнены из каталога с провенансом — решение получает fit.

### 5.4. Запись в БД

Результат шага — строки в selection_result (data_model.md §10.7):

- status ∈ (fit, needs_check, excluded),
- reason — объяснение (нарушенные ТТХ для excluded, недостающие данные для needs_check),
- rank — заполняется на шаге 5 для fit-решений; для excluded и needs_check — NULL.

### 6.2. Формула итогового скора

#### Общая формула

    Score = Σ (w_i × N_i)

Где:
- w_i — вес критерия (§6.1);
- N_i — нормализованное значение критерия, [0, 1];
- i — индекс критерия (7 или 8, в зависимости от типа объекта).

Score ∈ [0, 1]. Решения сортируются по убыванию Score.

Число критериев: склад и медучреждение — 7, аэропорт — 8 (инфраструктура
разделена на «инфраструктура» + «шум» в рамках общего блока 0.30).

#### Нормализация значений

Критерии в разных единицах (кг, мм, рубли, дБА, штуки). Каждый приводится к
безразмерной шкале [0, 1]. Линейная нормализация — простая, прозрачная,
объяснимая.

Тип 1. «Больше — лучше» — грузоподъёмность, УГТ:

    N_i = value / max_value

Тип 2. «Меньше — лучше» — габариты, точность, инфраструктура, шум, цена:

    N_i = min_value / value

Тип 3. Бинарный — кейсы:

    N_i = 1, если есть хотя бы один кейс; иначе 0

Критерий «Габариты» — единый скаляр max(Д, Ш, В) в мм; если хотя бы одно
из трёх измерений NULL — критерий не оценён.

Где:
- value — значение критерия у конкретного решения;
- max_value, min_value — лучшее значение по выборке решений со статусом
  fit (вычисляется на лету при каждом запуске подбора, не хранится в БД).

#### Источник значений

- value — из БД: solution (payload_kg, mass_kg, length_mm, width_mm,
  height_mm, positioning_accuracy_mm, charging_power_kw, noise_level_dba,
  price_rub, trl) и solution_case_link (для критерия «кейсы»).
- max_value / min_value — вычисляются по выборке fit-решений при каждом
  запуске подбора.
- Значения после дозаполнения ТТХ из открытых источников попадают в
  solution_characteristic и учитываются в нормализации наравне с колонками
  solution (data_model.md §2.1, §5.8).

#### Обработка NULL

- Если value = NULL — критерий не участвует в нормализации, вклад = 0.
  В интерфейсе — пометка «критерий не оценён». Это не понижает решение в
  статусе, но снижает Score относительно решений с заполненными ТТХ.
- Если NULL у всех решений выборки по критерию — критерий исключается из
  формулы для этой выборки; веса остальных нормализуются к 1.0
  (w_i_new = w_i_old / Σ w_j_old). В UI — уведомление «критерий X не оценён
  ни у одного решения».
- Краевой случай «единственный fit»: он лучший по всем критериям выборки —
  Score = 1.00, ранг 1; показывается как есть.

#### Объяснимость

Ранжирование объяснимо: пользователь видит критерии и вклад ключевых
факторов в итоговую оценку.

В интерфейсе отображается:
- итоговый Score;
- таблица вклада каждого критерия (число + диаграмма);
- пометка, если критерий не оценён (NULL);
- итоговое место в списке.

#### Округление

- Score — до сотых (2 знака).
- Вклад критерия — до тысячных (3 знака).
- Промежуточные вычисления — без округления, округление только на выводе.

## 7. Шаг 6. Ручное добавление

Пользователь может вручную добавить решение в сравнение, даже если оно не
вошло в автоматическую подборку, — с предупреждением.

### 7.1. Логика

1. Пользователь видит список решений, включая excluded и needs_check.
2. У каждого excluded — кнопка «Добавить вручную».
3. При нажатии — модальное окно с причиной исключения (например, «Ширина
   робота 900 мм больше прохода 800 мм»).
4. Пользователь подтверждает — решение попадает в сценарий.
5. В БД: запись в scenario_solution с is_manual = true, manual_reason
   заполняется причиной (data_model.md §10.6).

#### 7.1.1. Ограничение: только сценарии «покупка» и «RaaS»

Ручное добавление доступно ТОЛЬКО в сценарии `purchase` и `raas`. Сценарий
`base` — «текущий процесс без роботизации» (data_model.md §10.5) — решений
не содержит по определению: иначе теряется смысл
`ΔOPEX = OPEX_year_rob − OPEX_year_base` (economic_model.md §2.5) и всего
сравнения. Реализация: `POST .../scenarios/{scenarioId}/solutions` в base →
400 «Базовый сценарий не содержит решений по определению. Добавляйте решения
в сценарии «покупка» или «RaaS».» (и PUT состава с непустым списком — тоже
400); в UI (модалка добавления) base не предлагается в выборе сценария.
Автоматический подбор состав сценариев НЕ пишет вообще (шаг 5 пишет
только selection_result; сценарии создаются пустыми — §9).

### 7.2. Что это даёт

- Пользователь не ограничен автоматикой.
- Ответственность за выбор — на нём.
- В отчёте — пометка «добавлено вручную».

### 7.3. Ограничение

Ручное добавление не снимает критическое ограничение физически — робот всё
равно не проедет в узкий проход. Но позволяет сравнить, если пользователь
знает о планах расширения проходов или готов рискнуть.

## 8. Шаг 7. Сравнение

Пользователь сопоставляет решения по унифицированным техническим,
эксплуатационным и экономическим характеристикам.

### 8.1. Что считается унифицированным

Не все ТТХ, а те, что:
- заполнены у большинства решений в выборке,
- влияют на выбор,
- понятны пользователю.

Базовый набор для сравнения:
- Производитель (vendor.name).
- Цена (price_rub).
- Грузоподъёмность (payload_kg).
- Габариты (length_mm × width_mm × height_mm).
- Точность (positioning_accuracy_mm).
- Мощность зарядки (charging_power_kw).

### 8.3. Правила

- Минимум 2 решения для сравнения.
- Возможность сортировки по любой колонке.
- Подсветка различий (например, минимальная цена — зелёным, максимальная — красным).
- Источник и дата для каждой ТТХ — по клику (source_kind, source_url,
  source_date, is_confirmed).
- Ручные добавления — с пометкой (is_manual = true).

### 8.4. Хранение

В БД нет отдельной таблицы comparison. Сравнение — UI-операция над
scenario_solution. Выбранные решения хранятся там, состав сравнения
формируется на лету. Это соответствует принципу «всё, что фильтруется и
сортируется — колонки; снимки переменного состава — JSON или вычисление на
лету» (data_model.md §12).

## 9. Реализация в коде
- Модуль: me.yuugao.robomatch.selection.
- Точка входа: SelectionService.run(userId, projectId) — @Transactional.
- Порядок вызовов:
    1. loadConstraints (шаг 1+3: отрасли объекта через object_type_industry,
       эффективные значения параметров) и loadPool (шаг 2+3: пул решений
       по solution_application + 8 ТТХ EAV-поверх-колонок + кейсы).
    2. classify(...) — шаг 4 (fit / needs_check / excluded).
    3. rankFit(...) — шаг 5 (веса, нормализация, Score, rank).
    4. ScenarioService.ensureDefaultScenarios — bootstrap base/purchase/raas
       при первом запуске (сценарии создаёт модуль подбора, а не модуль
       экономики).
    5. saveResults(...) — UPSERT по UNIQUE (project_id, solution_id),
       несостоявшиеся пары удаляются.
- Хранение: selection_result — status/reason/rank (инварианты запуска);
  Score и вклад критериев НЕ хранятся — пересчёт на лету при чтении
  (data_model.md §12 «вычисление на лету»; GET /selection показывает
  зафиксированные статусы и свежие объяснения).
- Ручное добавление: ScenarioService.addSolutionManually.
- Гонки: параллельный run → DataIntegrityViolationException → 409
  «повторите» (повтор идемпотентен).
- Веса — константы кода (WEIGHTS по коду типа объекта); редактирование
  в UI не предусмотрено (см. §10).

## 10. Принятые решения по границам алгоритма

1. Порог отсечения по рангу не задаётся: Score ∈ [0..1], все
   прошедшие фильтры решения показываются с рангом.
2. Веса критериев — константы модуля; редактирование в UI не
   предусмотрено.
3. Score интерпретируется числом и вкладом критериев; отдельные
   категории («хорошо/удовлетворительно») не вводятся.
4. Если после фильтрации не осталось fit-решений — показывается
   пустой список без рекомендаций (причины исключения видны в
   результате подбора).
5. Сравнение доступно от 2 решений (включая excluded и
   needs_check при ручном добавлении).

История рассмотрения этих решений — в журнале закрытых вопросов
(docs/backlog/closed_questions.md).
