# Нефункциональные требования

## Требования

### Аппаратные требования

> Решение должно работать на стандартном персональном компьютере или ноутбуке пользователя через современный веб-браузер.

> Специальное оборудование и графические ускорители на стороне пользователя не требуются.

> Серверная часть может быть развернута на компьютере команды или в облачной инфраструктуре, доступной для демонстрации.

### Программные требования и архитектура

> Тип решения — веб-приложение с разделением клиентской и серверной частей.

> Допускается любой обоснованный технологический стек. Предпочтительно использование свободного ПО с открытым исходным кодом.

> Компоненты должны запускаться в контейнерах Docker. Необходимо предоставить Dockerfile и файл docker-compose.yml либо эквивалентную воспроизводимую конфигурацию.

> Для хранения данных должна использоваться реляционная или документо-ориентированная СУБД.

> Взаимодействие компонентов должно быть документировано. При наличии API рекомендуется спецификация OpenAPI.

> Архитектура должна обеспечивать добавление новых отраслей, объектов, параметров, решений и расчетных модулей.

> Внешние источники не должны быть единственной точкой отказа демонстрации. Конкурсная версия должна работать на заранее загруженных данных.

### Производительность

> Каталог, формы и сохраненные проекты должны открываться без заметных задержек при пилотной нагрузке до 50 одновременных пользователей.

> Расчет экономики должен выполняться не более чем за 10 секунд для типового проекта.

> Запуск или пересчет модели может занимать до 60 секунд. Пользователь должен видеть статус выполнения.

> Система должна корректно обрабатывать ошибки загрузки данных и не терять ранее сохраненный проект.

### Безопасность и данные

> Реализовать разграничение доступа в соответствии с ролями.

> Не хранить пароли в открытом виде.

> Обеспечить изоляцию проектов разных пользователей.

> Передавать данные по защищенному протоколу при размещении в сети.

> Не использовать реальные персональные данные и сведения ограниченного доступа в демонстрационном наборе.

> Предусмотреть удаление пользовательского проекта и связанных с ним загруженных файлов.

### Требования к качеству интерфейса

> Интерфейс должен быть русскоязычным, последовательным и понятным пользователю без специальных знаний в программировании.

> Ключевой сценарий от выбора объекта до получения расчета должен выполняться без обращения к инструкции.

> Поля должны содержать единицы измерения, подсказки и примеры значений.

> Ошибки и ограничения должны быть сформулированы понятным языком и содержать способ исправления.

> Интерфейс должен корректно работать при разрешении экрана от 1366×768.

### Источники данных и импорт

> Данные могут поступать из файлов и встроенной базы. Архитектура должна предусматривать последующее подключение API. В рамках конкурса интеграция с промышленными системами и государственными сервисами не обязательна.

> Команда должна предусмотреть программные интерфейсы для импорта данных об объектах, каталоге и расчетных нормативах.

### Документирование API

> Все реализованные API должны быть документированы.

## Что следует для реализации

### Аппаратные требования (реализация)
- Веб-приложение, доступ по браузеру.
- Без WebGL, GPU, специализированного ПО на клиенте.
- Сервер — Docker-контейнер, разворачивается локально или в облаке.

### Архитектура
- Разделение клиент/сервер: Next.js + Spring Boot.
- Стек: свободное ПО с открытым исходным кодом.
- Docker + docker-compose: одна команда `docker compose up` поднимает
  все сервисы (frontend + backend + db + adminer) без дополнительных
  флагов и ручных шагов. Профили допустимы только для вспомогательных
  сервисов (например, adminer).
- Воспроизводимая конфигурация: из чистого клона репозитория один `up`
  даёт работающую платформу на заранее загруженных данных.
- СУБД: PostgreSQL.
- OpenAPI через springdoc.
- Расширяемость: справочники и админка, без правки ядра.
- Демо не зависит от внешних источников: seed-данные в БД.

### Производительность (реализация)
- 50 одновременных пользователей — без заметных задержек.
- Расчёт экономики ≤ 10 секунд.
- Имитация ≤ 60 секунд + статус выполнения.
- Ошибки загрузки данных не теряют проект.

### Безопасность
- Роли: гость, пользователь, админ.
- Пароли в хеше (argon2 или bcrypt).
- Изоляция проектов: правило «user видит только свои».
- HTTPS при размещении в сети.
- Демо-данные: синтетические, без ПДн.
- Удаление проекта каскадно с файлами.

### UI
- Русский язык интерфейса.
- Сценарий без инструкции.
- Поля: единицы измерения, подсказки, примеры.
- Ошибки с понятным языком и способом исправления.
- Поддержка 1366×768.

### Источники данных и импорт (реализация)
- Демо-режим: файлы организатора + встроенная база (seed), без обязательных внешних API.
- Архитектура допускает последующее подключение API источников данных.
- Импорт данных (объекты, каталог, нормативы) — программные интерфейсы модуля /import.
- Интеграции с промышленными системами и государственными сервисами — вне рамок текущей версии.

### API
- Все эндпоинты документированы.
- OpenAPI генерируется из контроллеров.
