# Подбор и рекомендации решений

## Требования

### Формирование списка применимых решений
> Формировать список применимых типов решений и конкретных продуктов на основании параметров объекта и ограничений продукта.

> Платформа определяет применимые типы роботизации, показывает конкретные продукты и объясняет причины включения или исключения решения.

### Причины соответствия и ограничения
> Для каждого результата показывать причины соответствия, ограничения и недостающие данные.

### Логика исключения
> Не рекомендовать продукт, если ключевое ограничение делает его использование невозможным. При недостатке данных решение может быть отмечено как требующее проверки.

### Ручное добавление
> Позволять пользователю вручную добавлять решение в сравнение, даже если оно не вошло в автоматическую подборку, с отображением предупреждения.

### Объяснимость ранжирования
> Ранжирование должно быть объяснимым. Пользователь должен видеть критерии и вклад ключевых факторов в итоговую оценку.

### Сравнение решений
> Пользователь сопоставляет решения по унифицированным техническим, эксплуатационным и экономическим характеристикам.

### Условия исключения неподходящих решений
> Условия исключения неподходящих решений. Команда формирует правила фильтрации решений по техническим характеристикам, инфраструктуре и контекстным ограничениям (например, габариты, масса, точность позиционирования, требования к безопасности) и описывает их в допущениях.

## Что следует для реализации

### Входные данные
- Параметры объекта (из `project_parameter_value`).
- Тип объекта (склад, аэропорт, медицина).
- Каталог решений (из `solution` + `solution_application`).
- Обязательные ТТХ решений (из `solution` + `solution_characteristic`).

### Алгоритм подбора
1. **Определить отрасли** — маппинг «тип объекта → отрасли» (`object_type_industry`).
2. **Отфильтровать решения** — по отрасли через `solution_application`.
3. **Проверить обязательные ТТХ** — габариты, масса, точность, инфраструктура.
4. **Исключить непригодные** — если критическое ограничение нарушено.
5. **Пометить «требует проверки»** — если данных не хватает.
6. **Ранжировать** — по критериям с видимыми весами.

### Статусы решений после подбора
- **fit** — подходит.
- **needs_check** — требует проверки (не хватает данных).
- **excluded** — исключено (критическое ограничение).

Ручное добавление решения — не статус подбора: добавление фиксируется
флагом `scenario_solution.is_manual` (data_model.md §10.6).

### Причины включения / исключения
Для каждого решения сохранять:
- Список критериев, по которым прошло.
- Список ограничений.
- Список недостающих данных (если needs_check).
- Текст-объяснение для UI.

### Ранжирование
Критерии (примерные, финальные — в `selection_algorithm.md`):
- Соответствие габаритам и проходам.
- Грузоподъёмность vs масса грузовой единицы.
- Точность позиционирования vs требования.
- Инфраструктурные требования vs доступные мощности.
- Цена vs бюджет (если указан).
- УГТ (готовность технологии).

Веса — в `selection_algorithm.md`. Пользователь видит вклад каждого критерия.

### Ручное добавление (реализация)
- Пользователь может добавить решение в сравнение, даже если оно excluded.
- При добавлении — показывается предупреждение с причиной исключения.
- Добавление фиксируется флагом `scenario_solution.is_manual` с причиной
  `manual_reason` (data_model.md §10.6).

### Сравнение
- Минимум 2 решения.
- Унифицированные характеристики: ТТХ, экономика, применимость.
- Таблица сравнения с возможностью сортировки.

### Данные из открытых источников
- ТТХ, дозаполненные из открытых источников, используются в подборе.
- Если ТТХ нет — решение может попасть в `needs_check`.
- Источник и дата — отображаются в карточке.
