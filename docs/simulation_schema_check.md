Живой стек: backend :8080, frontend :3100, проект 4 «Пиковая нагрузка»
(сценарий purchase, 5 роботов, 2 зарядные станции, узкое место

Источники истины: `docs/requirements/simulation.md` (дословные выжимки

## 1. Где роботы останавливаются

### 1.1 Остановки строго в точках операций

Фаза «загружается/разгружается» жёстко привязана к точке операции
(assumptions.md §22-бис): робот доходит до точки, останавливается
точно в её центре и стоит там суммарно `sim_pick_drop_sec` модельного
времени — две фазы по половине: погрузка в точке A и разгрузка в
точке B (ближайшая соседняя — очередь точек «по порядку»).

Расписание робота внутри цикла (модельное время; `computeWindows` в
SimulationView.tsx, длина цикла = `sim_pick_drop_sec / handlingPct` —
доли KPI сохраняются точно):

```
[0, M)            чистое движение по кольцевому маршруту
[M, M+a)          подход: доезд ПО МАРШРУТУ до стыка (ближайшая к A
                  точка маршрута) + Г-образный сход к A
[M+a, M+a+h)      ПОГРУЗКА — строго в точке A (h = pickDrop/2)
[M+a+h, +t)       переезд A → B (короткий, соседняя точка)
[M+a+h+t, +h)     РАЗГРУЗКА — строго в точке B
далее             возврат (Г-образный сход + маршрут) и простой
```

Координаты точек операций (центры иконок; робот стоит ровно здесь,
±2 px — проверено e2e-поллингом data-x/data-y):

| Зона                      | Точки (viewBox 960×480)                                                         |
|---------------------------|---------------------------------------------------------------------------------|
| Приёмка — полки 26×22     | (61,161) (61,217) (61,273)                                                      |
| Хранение — стеллажи 64×20 | (262,160) (344,160) (426,160) (508,160) (262,252) (344,252) (426,252) (508,252) |
| Отбор — корзины 16×12     | (262,430) (314,430) (366,430) (418,430) (470,430) (522,430)                     |
| Отгрузка — доки 26×22     | (699,161) (699,217) (699,273)                                                   |

Автопроверки (verify_simulation_schema_semantics.py, сэмплы 5×):
в handling координаты совпадают с одной из точек ±2 px; координаты
стабильны всю фазу; фаза ≈ pickDrop/2; погрузка + разгрузка =
pickDrop; фазы «движется»/handling не пересекаются.

Геометрия маршрута проведена ВНЕ всех текстов с запасом на корпус
робота (±7,5), след движения (±9) и толщину линий: вертикали
x=185/385/772, верхняя нитка y=70, горизонталь y=190; Г-образные
сходы идут через стык маршрута (вертикаль по x стыка → горизонталь
на высоте точки) — не пересекают ни одну подпись или бейдж.

| Вопрос                                    | Как реализовано                                                                                                                                                                                                                                                                                                                                  | Источник                                                                                        |
|-------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------|
| Остановка в точках операций               | Да, строго в центрах иконок (таблица выше); `LOOP` — кольцо «приёмка → хранение → отбор → отгрузка → зарядный блок» из 7 точек; travelRef не растёт вне фазы «движется»                                                                                                                                                                          | simulation.md «точки выполнения операций»; assumptions §22-бис                                  |
| Остановка на зарядных станциях            | Частично: зарядный блок — зона схемы с иконками станций; кольцевой маршрут проходит через него, простаивающие роботы стоят на маршруте (в т.ч. в зарядном блоке — фазы распределены). Отдельной анимации «подъезд к станции» нет — зарядка свёрнута в статус «Простаивает (зарядка/ожидание)» (агрегированный учёт через K_availability, см. §3) | simulation.md «точки … зарядки» — точки отображены; интерпретация зарядки — assumptions §22-бис |

## 4. Перекрытие текста элементами схемы (0 перекрытий на 4×2)

Headless-проверка (Playwright + getBoundingClientRect; порог 1 px по
каждой оси, исключая вложенные tspan/text):

- Текст × текст — все подписи схемы;
- Текст × препятствия — роботы (в ЛЮБОЙ фазе), иконки операций и
  станций, детали path; линии (маршрут, потоки, стрелки) — ПОСЕГМЕНТНО
  (Liang-Barsky c запасом на толщину штриха: bbox замкнутой полилинии
  охватил бы всю схему и дал бы ложные срабатывания);
- Рамка узкого места (fill="none" контур) не препятствие — текст
  внутри рамки читается.

Проверяется на 4 разрешениях × 2 ТЕМЫ (8 прогонов): 1366×768,
1920×1080, 375×812, 768×1024 — 0 перекрытий везде. Дополнительно:
длительный перехват (220 сэмплов, ~275 с модельного времени на 5×) —
0 перекрытий во всех фазах роботов. Визуальный контроль:
`docs/examples/schema-review/` — полная схема + зоны + легенда в обеих
темах (14 PNG; проверены и глазами).

Геометрия без пересечений спроектирована, а не подогнана: нитки
маршрута вне текстов (§1.1), строка зоны «{поток} п/ч · загрузка {N}%»
одна (бейдж ниже не задевает), бейдж «Узкое место: X%» (в узких зонах
«Узкое: X%») не доходит до вертикали маршрута, подписи паллет — ПОД
иконками операций внутри своих зон (плашки 40..158 и 600..722 на
y=286..304), Г-образные сходы/переезды — по «коридорам» между
текстами.

Автопроверка закреплена в `scripts/verify_simulation_schema_semantics.py`
(блоки «Перекрытия» и «Подписи паллет»). Раскладка зон внутри viewBox
спроектирована без пересечений плашек (имена зон — у верхних углов зон,
легенда — отдельный блок 765×248..935×460, потоки — между зонами).

## 7. Известные ограничения (журнал closed_questions.md)

- Пик производительности считается двумя путями (сервис/модель),
  Δ≈1,5e-6 оп/ч — на округлении 0,1 не проявляется.
- Порог расхождения KPI↔экономика при сверке — 1%
  (DIVERGENCE_EPSILON в SimulationModel).
- Дефолты sim_* дают системный зазор модель vs P_effective
  (калибровка — вопрос к данным).
- Параллельные экспорты схемы перезаписывают latest-строку сценария.
- Порог 60 с: backend помечает failed, а требование предполагает
  предупреждение (практически недостижимо — ~40 мс).
- next-env.d.ts перегенерируется в dev (шум в git status).

Итоговые счётчики проверок: модель — 154/154 пересчётов совпадают (8
сценариев × 19 метрик + 2 edge: пустой состав → 400 «Состав сценария
пуст», k_availability=0 → failed с понятной ошибкой); KPI↔экономика —
инварианты (selectedRobots=Σqty, P_effective=P_nominal×K_load×
K_availability, nInfra=ceil(N×ratio)) на 4 проектах + провокация
расхождения (изменение qty без пересчёта → предупреждение «Состав
изменён»); UI — 59/60 (единственный сбой — консольные предупреждения
React, устранены); требования — 6/7 пунктов полностью, 7-й
(PDF-экспорт) закрыт; экспорт — 15/15 (санитизация XSS-корпус,
изоляция чужих схем 404, удаление с проектом, скачивание).
