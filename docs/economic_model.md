# Экономическая модель

## Назначение

Документ описывает правила и формулы расчёта платформы.
Источник правды для кода расчётного модуля.

Требования - в `requirements/economics.md`.
Допущения - в `docs/assumptions.md`.
Связь с другими документами - `docs/architecture.md`, `docs/data_model.md`.

## 1. Входные данные

Конкретизация источников:
параметры объекта читаются из `project_parameter_value` (значение проекта
или дефолт `object_type_parameter`), ТТХ решений - из каталога (зеркальные
колонки + EAV `solution_characteristic`), допущения - из редактора
допущений (каталог `assumptions.md` §22–23, переопределения -
`project_assumption`). Эффективное значение = переопределение
пользователя, иначе дефолт каталога. Состав сценария - `scenario_solution`
(подбор + ручные добавления).

### 1.1. Из параметров объекта
- Peak_demand - пиковая потребность в операциях, операций/час.
- Hours_year - режим работы, часов/год.
- FOT_base - фонд оплаты труда в базовом сценарии, руб./год.
- N_staff_base - численность персонала в базовом сценарии, чел.

Деривации из параметров склада (assumptions.md §2 - 26 обязательных параметров):
- Peak_demand = (паллет приёмки + паллет отгрузки в сутки) / часы
  работы в сутки × пиковый коэффициент (peak_load_factor);
- Hours_year = смены × продолжительность смены × рабочих дней в году;
- Operations_year = (приёмка + отгрузка) × рабочих дней в году
  («операция» = паллета-перемещение); объём отбора (строк/сутки) -
  вход подбора, в экономику не входит;
- FOT_base = (зарплата отборщика × отборщики + зарплата оператора
  погрузчика × операторы) × 12 × K_начислений - контур роботизации
  (целевые группы), а не весь склад;
- Salary_year - средневзвешенная годовая зарплата контура.

### 1.2. Из каталога решений
- P_nominal - номинальная производительность робота, операций/час.
  В EAV каталога числовой характеристики нет (`productivity` - текст):
  задаётся допущением `robot_nominal_productivity_per_hour` (§1.3).
- K_availability - коэффициент доступности, [0..1], если указан в ТТХ.
  В каталоге данных о доступности нет - нейтральное значение задаётся
  допущением (§1.3), простои уже учтены в K_load.
- Price_robot - цена робота, руб., с НДС (зеркальная колонка каталога;
  средневзвешенная по количеству в составе - `avg_robot_price`).
- Lifetime - срок службы, лет (ТТХ, средневзвешенно по количеству;
  отсутствует - допущение `amortization_years`, §1.3).
- P_consumption - потребляемая мощность, кВт. Числовой характеристики
  в EAV нет: значение задаётся допущением `robot_power_consumption_kw`;
  фолбэк - ТТХ «мощность зарядного устройства» (`charging_power_kw`,
  консервативная оценка сверху); иначе - 0 с предупреждением в расчёте.
- Количество роботов N_robots - сумма `quantity` состава сценария
  (состав × количество; расчёт не «дозаказывает» парк сам).

### 1.3. Из допущений пользователя
Каталог кодов с дефолтами и диапазонами - assumptions.md §22–23
(коэффициенты экономики) и §22-бис (входы расчётного модуля).
- K_load - коэффициент загрузки, [0..1].
- K_reserve - коэффициент резерва, [0..1].
- Tariff - тариф на электроэнергию, руб./кВт·ч.
- Salary_year - годовая зарплата одного сотрудника, руб.
  (производная средняя контура - §1.1; отдельного допущения нет).
- K_начислений - коэффициент страховых взносов, 1.302 = 1 + 30.2%
  (хранится уже с единицей, §2.4).
- C_infra, C_software, C_integration, C_commissioning, C_training, C_reserve - статьи CAPEX.
- C_service, C_licenses, C_communication, C_consumables, C_repair - статьи OPEX.
- Horizon - горизонт расчёта, лет. По умолчанию 5.
- Amort_method - метод амортизации: константа реализации - линейный.
- Rate - ставка по заёмным средствам, % годовых (если применимо).
- RaaS_payment_model - модель платежей RaaS: fixed, usage, mixed (§2.11).
- RaaS_rate_month - фиксированная месячная ставка RaaS: в каталоге
  допущений задаётся в % цены робота (raas_rate_month_pct,
  1.5–3% - assumptions.md §23); месячный платёж руб./робот =
  цена × ставка% / 100 (§2.11, без промежуточного округления - §4).
- RaaS_contract_years - срок контракта RaaS, лет (по умолчанию 3,
  assumptions.md §23).
- RaaS_buyout - флаг выкупа в конце контракта.
- K_availability, P_nominal, P_consumption, N_staff_rob, dOther,
  фактор стоимости оборудования, ставка за операцию, параметры
  кредита - входы расчётного модуля (assumptions.md §22-бис).

## 2. Формулы

### 2.1. Количество роботов
K_reserve трактуется как РЕЗЕРВНАЯ НАДБАВКА к пиковой нагрузке
(«с резервом 15–20%», Легенда XLSX, assumptions.md §22) - потребность
умножается на (1 + K_reserve), что эквивалентно делению эффективной
производительности на (1 + K_reserve):
P_effective = P_nominal × K_load × K_availability
requiredRobots = ceil( Peak_demand × (1 + K_reserve) / P_effective )

ТЕРМИНОЛОГИЯ (разделяется кодом и UI):
- **requiredRobots - рекомендация по пиковой нагрузке** (формула выше;
  проверка достаточности состава);
- **selectedRobots - фактический состав сценария** = sum(quantity)
  строк scenario_solution (состав × количество);
- **вся экономика (CAPEX, OPEX, эффект, TCO, платежи RaaS) считается
  по selectedRobots** - расчёт не «дозаказывает» парк сам.

Если selectedRobots < requiredRobots - флаг underpowered и
предупреждение «расчёт не отражает достижение заявленной
производительности» (мягкая плашка, не ошибка; жёсткий
запрет недостаточного парка - применяется к подбору, не к экономике).
Проверки парка и предупреждения о пустом составе НЕ применяются
к базовому сценарию: он не содержит решений по определению
(инвариант base, см. data_model.md §10.5) - пустой
состав base - норма, а не недобор.
Округление всегда вверх. K_availability берётся из ТТХ, если есть;
иначе - из допущений. Если P_nominal задан, а знаменатель
P_nominal × K_load × K_availability = 0 (например, K_availability = 0) -
формула неприменима: requiredRobots не рассчитывается (null),
расчёт продолжается. На чувствительность (§2.12) этот знаменатель
не влияет: объём операций масштабирует ВЫБРАННЫЙ парк
пропорционально Δ% при любых ТТХ.

### 2.2. Вспомогательное оборудование
N_infra = ceil(selectedRobots × Ratio_infra)
(зарядные станции - целые единицы; округление вверх, §4)
Ratio_infra - количество единиц инфраструктуры на одного робота (зарядки, док-станции). Допущение.

### 2.3. CAPEX
C_equipment = Σ ( quantity × Price_robot ) по строкам выбранного состава
CAPEX = C_equipment + C_infra + C_software + C_integration
      + C_commissioning + C_training + C_reserve

C_reserve рассчитывается как процент от суммы предыдущих статей:
C_reserve = Reserve_rate × ( C_equipment + C_infra + C_software
           + C_integration + C_commissioning + C_training )

Цены - с НДС. Доставка, пусконаладка и интеграция в цену не входят, считаются отдельно.

### 2.4. OPEX годовой
C_electricity = Σ ( quantity_i × P_consumption_i ) × Hours_year × Tariff
(по строкам выбранного состава; эквивалент - средневзвешенная мощность
× selectedRobots)
C_staff = N_staff_rob × Salary_year × K_начислений
OPEX_year = C_service + C_licenses + C_electricity + C_communication
          + C_consumables + C_repair + C_staff

N_staff_rob - численность персонала эксплуатации в роботизированном сценарии
(допущение). K_начислений - коэффициент страховых взносов: в датасете
хранится уже с единицей (`payroll_insurance_contributions_rate` = 1.302 =
1 + 30.2%), формула умножает без добавления единицы (assumptions.md §22).

### 2.5. Изменение OPEX
OPEX_year_base - операционные затраты базового сценария; для склада
это ФОТ целевых групп контура роботизации (OPEX_base = FOT_base, §1.1)
- прочие статьи базового процесса вне контура не сравниваются.
ΔOPEX = OPEX_year_rob - OPEX_year_base

Отрицательное значение - экономия. Положительное - рост затрат.

### 2.6. Годовой эффект
ΔFOT = FOT_base - FOT_rob
FOT_rob = C_staff (§2.4, с K_начислений)
Effect_gross = ΔFOT + ΔOther - ΔOPEX_без_ФОТ
Amort_year = CAPEX / Lifetime
Effect_year = Effect_gross - Amort_year

ΔFOT учитывается ТОЛЬКО при selectedRobots > 0: пустой состав роботизированного сценария -
замещения персонала нет, ΔFOT = 0, Effect_gross = 0 + ΔOther -
ΔOPEX_без_ФОТ (статьи пустого состава нулевые → Effect_gross = ΔOther,
амортизация 0 → Effect_year = Effect_gross).

Effect_year - эффект ПОСЛЕ амортизации; не является денежным потоком
(амортизация - учётная величина, а не платёж; денежные потоки - CAPEX
и OPEX). UI показывает раздельно: «эффект до амортизации»
(Effect_gross) и «амортизация» (Amort_year) отдельными строками.

БЕЗ ДВОЙНОГО СЧЁТА: изменение ФОТ входит в эффект отдельным слагаемым
ΔFOT, поэтому из OPEX в эффекте вычитается только часть БЕЗ ФОТ
(ΔOPEX_без_ФОТ = Payment/C_service/C_licenses/C_electricity/
C_communication/C_consumables/C_repair). Полное ΔOPEX (с ФОТ, §2.5) -
самостоятельная строка таблицы сравнения, в эффект не подставляется.
ΔOther - прочие измеримые эффекты: предотвращённые потери, дополнительный доход.
Amort_year - линейная амортизация (константа реализации).

### 2.7. Срок окупаемости
Payback = CAPEX / Effect_year

Применяется только при Effect_year > 0 (Effect_year - после вычета
аннуитета, если задан кредит - §2.10). Иначе - статус «не окупается», числовое значение не выводится.
CAPEX = 0 (RaaS без выкупа / пустой состав) - «окупаемость не определена»,
сравнение по годовому эффекту и TCO. Сверхдолгая окупаемость (расчётный
порог 1 млн лет) - числовое значение не выводится, статус «не окупается
в разумный срок» (защита колонки, аналогично ROI).

### 2.8. ROI
Накопленный эффект за горизонт:
CumEffect = Σ ( Effect_year_t ) для t = 1..Horizon
ROI = ( CumEffect / CAPEX ) × 100%

Effect_year_t - годовой эффект в год t. Для упрощения принимается равным Effect_year, если не задана динамика.
CAPEX = 0 - ROI не определён (RaaS без выкупа: сравнение по годовому
эффекту и TCO, «Н/П»). Сверхвысокая доходность (расчётный порог
1 млрд %, |ROI| сверх порога) - числовое значение не выводится,
статус «ROI вне представимого диапазона» (защита колонки numeric(12,2),
зеркально порогу окупаемости §2.7).

### 2.9. TCO
TCO = CAPEX + Σ ( OPEX_year_t ) + Σ ( Replacements_t )
Replacements_t - замена основных компонентов в год t. Определяется по сроку
службы компонента. Полная замена парка оборудования
C_equipment каждые Lifetime лет - количество замен
floor((Horizon - 1) / Lifetime), стоимость = количество × C_equipment.
Замена АКБ отдельно НЕ считается - уже включена в C_consumables
(«вкл. АКБ по сроку 3–5 лет», assumptions.md §22).

TCO RaaS:
TCO_raas = CAPEX_raas + Payment_year × годы_платежей
         + ( C_electricity + C_communication + C_staff ) × Horizon
Платежи идут годы min(контракт, горизонт) при реальном выкупе
(CAPEX_raas > 0) - после выкупа платежи прекращаются; без выкупа -
весь горизонт (тогда формула вырождается в OPEX_raas × горизонт).
Прочий OPEX (электроэнергия, связь, персонал эксплуатации) идёт
ВЕСЬ горизонт - роботы работают и после выкупа/окончания контракта;
выкуп единоразово в CAPEX_raas (второй раз не прибавляется).

### 2.10. Заёмное финансирование
Если сценарий с заёмными средствами:
Debt_payment_year = Loan_amount × ( Rate × ( 1 + Rate )^Term ) / ( ( 1 + Rate )^Term - 1 )
effectYearBeforeDebt = Effect_gross - Amort_year (= Effect_year без кредита)
Effect_year = effectYearBeforeDebt - Debt_payment_year

Loan_amount, Term, Rate - из допущений. ПОРЯДОК:
annualDebtPayment (аннуитет) вычитается из Effect_year ДО расчёта
Payback/ROI - окупаемость и доходность считаются от эффекта после
обслуживания долга. TCO обслуживание долга НЕ включает (это
финансирование, не владение).

### 2.11. RaaS («роботы как услуга»)
Сценарий RaaS обязателен (по условиям конкурсного набора) и сравнивается с базовым
и покупкой по единым показателям: CAPEX, OPEX, годовой эффект, окупаемость, ROI.
Модель и допущения - assumptions.md §23 (фиксированная ставка, контракт 3 года,
опциональный выкуп по остаточной стоимости).

Структура платежей зависит от выбранной модели (N_robots =
selectedRobots - выбранный состав):
- fixed: Payment_year = 12 × RaaS_rate_month × selectedRobots
- usage: Payment_year = Usage_rate × Operations_year
- mixed: Payment_year = 12 × RaaS_rate_month × selectedRobots + Usage_rate × Operations_year

OPEX_year_raas = Payment_year + C_electricity + C_communication + C_staff

CAPEX_raas - минимальный или 0 (контракт без выкупа): оборудование принадлежит
оператору услуги. Если нужны инфраструктурные работы на стороне эксплуатанта -
C_infra_site в CAPEX_raas (обоснование - в допущениях расчёта).

Выкуп по остаточной стоимости (линейная амортизация):
Buyout_value = Price_robot × max(0, 1 − RaaS_contract_years / Lifetime)
CAPEX_raas = selectedRobots × Buyout_value (0 при контракте без выкупа;
остаточная доля ≤ 0 - выкуп не считается)
Амортизация выкупной части - по остаточному сроку службы:
Amort_raas = CAPEX_raas / (Lifetime − RaaS_contract_years)
Платежи идут годы min(контракт, горизонт) только при реальном
выкупе (остаточная доля > 0, CAPEX_raas > 0) - после выкупа
платежи прекращаются; без выкупа (и при остаточной доле ≤ 0)
платежи идут весь горизонт.

Эффект и окупаемость RaaS (без двойного счёта - как в §2.6: ΔFOT
учитывает ФОТ отдельно, из OPEX в эффекте вычитается часть БЕЗ ФОТ):
Effect_year_raas = ΔFOT + ΔOther − OPEX_year_raas_без_ФОТ − Amort_raas
Payback_raas = CAPEX_raas / Effect_year_raas (при CAPEX_raas = 0 - сравнение по
годовому эффекту и TCO, окупаемость не определена - выводится сообщение).
TCO_raas = CAPEX_raas + Payment_year × годы_платежей
         + ( C_electricity + C_communication + C_staff ) × горизонт
(при выкупе годы_платежей = min(контракт, горизонт), без выкупа -
весь горизонт; выкуп уже в CAPEX_raas - второй раз не прибавляется).
Прочий OPEX (электроэнергия/связь/персонал) идёт ВЕСЬ горизонт - роботы
работают и после выкупа; при детальном ТЭО - пересмотреть состав статей.

Правила:
- параметры RaaS (ставка, срок, выкуп) - изменяемые допущения,
  фиксируются в расчёте (calculation_assumption);
- допускается упрощённая модель платежей (фиксированная ставка), но
  сценарий RaaS из сравнения не убирается.

### 2.12. Чувствительность
Для каждого параметра из набора (стоимость оборудования, объём операций, стоимость труда):
Изменяем параметр на Δ%
Пересчитываем Effect_year, Payback, ROI
Возвращаем таблицу «Δ параметра → Δ показателя»

Шаг Δ% по умолчанию: -20, -10, 0, +10, +20. Пересчёт - полным
движком на масштабированном входе: оборудование -
цены × (1 + Δ) (фактор стоимости не трогается - один рычаг);
ОБЪЁМ ОПЕРАЦИЙ - чувствительность по объёму
отвечает на вопрос «что будет с экономикой, если парк увеличить
пропорционально»: выбранный состав масштабируется пропорционально Δ%,
scaledTotal = ceil( selectedRobots × (1 + Δ) ),
распределение по строкам состава - методом наибольших остатков
(Σ ровно scaledTotal); годовой объём × (1 + Δ); персонал
эксплуатации масштабируется вместе с парком (доля парка, не доля
Δ%). P_nominal в масштабировании НЕ участвует: строка Δ=0
воспроизводит основной результат при ЛЮБОМ составе. Труд - ФОТ контура и зарплата × (1 + Δ),
dOther НЕ масштабируется. Чувствительность считается для каждого
роботизированного сценария (покупка и RaaS).
Пустой состав в модели usage: платежи за операции обнуляются
(предупреждение) - операции выполнять некому.

### 2.13. Формирование результата

Результат расчёта - таблица сравнения сценариев.
Строки - показатели: selectedRobots (и requiredRobots при заданном
P_nominal), CAPEX, OPEX_year, ΔOPEX, ΔFOT, Effect_year, Payback,
ROI, TCO.
Колонки - сценарии: базовый, покупка, RaaS.
Дополнительно: Δ к базовому, интерпретация Payback, флаг недобора
парка (underpowered), флаг превышения (overpowered - нейтральная
информация «возможна переплата»), чувствительность.

## 3. Порядок расчёта

1. Валидация входных данных.
2. Расчёт количества роботов и инфраструктуры.
3. Расчёт CAPEX.
4. Расчёт OPEX и ΔOPEX.
5. Расчёт Effect_year с учётом амортизации.
6. Расчёт Payback, ROI, TCO.
7. Расчёт сценария RaaS (если выбран).
8. Расчёт чувствительности.
9. Формирование результата: показатели, формулы, источники, допущения.

## 4. Правила

- Все коэффициенты - из `docs/assumptions.md` или из условий конкурсного набора.
- Недокументированные коэффициенты запрещены.
- Все формулы видны пользователю в интерфейсе и отчёте.
- Единицы измерения обязательны для каждого поля.
- Ручная корректировка значения фиксируется: исходное, новое, дата, автор, причина.
- При Effect_year ≤ 0 - Payback не рассчитывается, выводится сообщение.
- Округление N_robots - всегда вверх.
- Округление стоимостных показателей - до рублей.
- Округление Payback - до десятых года.
- Округление ROI - до десятых процента.
- Отображение окупаемости - человекочитаемо, целыми значениями:
  payback < 1/12 года → «до 1 месяца»; 1 мес. ≤ payback
  < 12 мес. → целые месяцы, округление ВВЕРХ - 1,2 мес. → «2 месяца»,
  11,4 мес. → «12 месяцев»; 1 год ≤ payback < 5 лет → годы и месяцы -
  «1 год 3 месяца», 0 месяцев → «2 года»; payback ≥ 5 лет → целые
  годы, округление вверх - 5,1 г. → «6 лет», 7,0 г. → «7 лет».
  Округление вверх - не занижать срок окупаемости. Поле paybackMonths
  (round(payback × 12, 1) при сроке < 0,5 года) сохраняется в DTO для
  отчёта и API; UI рендерит человекочитаемую строку
  (InterpretationDto.paybackHuman; зеркальные реализации -
  InterpretationFormatter на backend и formatPaybackShort в
  types/economics.ts). Правило касается только форматирования вывода.

Интерпретация Payback:
- Payback ≤ 3 лет - быстрая окупаемость.
- Payback 3–5 лет - умеренная.
- Payback > 5 лет - долгая, требует обоснования.
- Effect_year ≤ 0 - не окупается.

## 5. Версионирование расчёта

Каждый расчёт хранит:
- Calculation_id
- версия исходных данных (хеш или номер)
- версия расчётной модели
- дата и время
- список использованных допущений
- список ручных корректировок

Формат версий:
- version_data = первые 12 hex-символов SHA-256 канонического снимка
  входов (параметры + эффективные допущения + состав с ценами и ТТХ
  решений, отсортированные по имени/идентификатору): одинаковые
  входы - одинаковая версия, воспроизведение проверяемо;
- version_model = «economic-model-1.0» - версия формул (меняется при
  изменении расчёта разделов 2–4);
- скорректированный расчёт наследует
  version_data исходного - входы те же, вмешательство зафиксировано
  в записи корректировки и блоке adjustedFrom metrics_json.

При повторном открытии проекта расчёт воспроизводится с той же версией данных и модели.
Ручные корректировки входят в Calculation_version.
При воспроизведении расчёта корректировки применяются
в том же порядке и с теми же значениями.

## 6. Обработка ошибок

- Некорректные типы - ошибка валидации, поле подсвечивается.
- Значения вне диапазона - предупреждение или ошибка.
- Нулевые или отрицательные значения в знаменателе - блокировка расчёта.
- Отсутствие обязательных данных - расчёт не выполняется, выводится список недостающего.
- Ошибки формулируются понятным языком, со способом исправления.

## 7. Производительность

- Расчёт экономики ≤ 10 секунд для типового проекта.
- Пересчёт модели ≤ 60 секунд, статус выполнения виден пользователю.
- Ошибки не теряют ранее сохранённый проект.

## 8. Ограничения

- Платформа не заменяет детальное проектирование и обследование объекта.
- Результат - предварительная оценка, требует верификации.
- Точность зависит от полноты входных данных.
- Расчёт не учитывает налоговые режимы, кроме НДС в ценах.
- Амортизация - линейная по умолчанию.
- При большом baseline ФОТ (много целевого персонала) расчёт даёт
  очень быструю окупаемость и сверхвысокий ROI. Это математически корректный результат, но
  требует проверки на реальных данных: baseline = ФОТ целевых групп
  (отборщики + операторы погрузчиков), прочие текущие расходы в
  baseline не учтены (assumptions.md §22) - полная замещаемость
  контура на практике недостижима. UI показывает подпись под
  ROI > 500%: «Значение зависит от большого baseline ФОТ - проверьте
  допущения»; та же сноска предусмотрена в шаблоне отчёта.
