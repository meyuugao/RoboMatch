## 1. Маппинг «тип объекта → отрасли каталога»

### Что
Отрасль в каталоге - поле `Отрасль` из `catalog_export_v4.csv` (9 значений).
Тип объекта выбирает пользователь (склад, аэропорт, медицина).
Прямого соответствия в данных нет - задаём вручную.

### Значения
- Склад → Торговля и услуги, Промышленность, Транспорт и логистика
- Аэропорт → Транспорт и логистика, Безопасность
- Медучреждение → Безопасность, Торговля и услуги

### Прямая связь «решение ↔ тип объекта»
Не создаётся. Применимость выводится через object_type_industry:
тип объекта → отрасли → решения. Это соответствует требованию конкурсной документации («поддерживаемые типы объектов»),
но не требует ручного проставления 187×3 связей.

### Источник
Конкурсная документация (иерархия), `catalog_export_v4.csv` (поле `Отрасль`), `Датасеты_хакатон.xlsx` (3 типа).

### Обоснование
Маппинг не задан в конкурсной документации и не выводится из данных автоматически. Склад и аэропорт напрямую не названы в отраслях. Медучреждение в CSV отсутствует как отрасль.

### Влияние
Без маппинга подбор не находит решения. Используется в `selection_algorithm.md`. Реализуется через `object_type_industry` (7 связей).

«тип объекта → отрасли» или подтверждение.

## 2. Обязательные параметры объектов

#### Аэропорт
Обязательные для расчёта экономики (22): площадь терминала, количество терминалов, количество гейтов, пассажиропоток, среднесуточные пассажиры, пиковые пассажиры в час, среднесуточные рейсы, пиковые рейсы в час, TAT, операций на рейс, объём багажа, масса багажа, численность рамп, численность терминала, з/п рамп, з/п уборщика, коэффициент начислений, режимных зон, уровень шума, температура в неотапливаемых зонах, площадь перрона, требования airside.

Опциональные (12): количество ВПП, стойки регистрации, карусели багажа, бортовое питание, заправка ВС, грузовые тележки, уборочные машины, вывоз мусора, наличие FIDS/AODB, мощность зарядки, бюджет CAPEX, горизонт расчёта.

Обязательные для выбора решений (5): обеззараживание, шум в палатах, наличие СКУД, материал поверхностей, управление лифтами.

Опциональные (16): амбулаторные посещения, расстояние до отделения, точки раздачи питания, наименований медикаментов, заявок на медикаменты, доля срочных, точки сбора отходов, периодичность вывоза, количество КДЛ, время доставки пробы, наличие МИС, наличие ЛИС, наличие пандусов, мощность зарядки, бюджет CAPEX, горизонт расчёта.

### Источник
Конкурсная документация (минимальный набор параметров), `Датасеты_хакатон.xlsx`.

### Обоснование
Конкурсная документация задаёт минимальный набор. Обязательность для расчёта определяется по тому, какие параметры нужны для формул экономики и подбора.

### Влияние
`is_required = true` в `object_type_parameter`. Без обязательных расчёт не запускается.
Значения по умолчанию - базовые из датасета.
Минимум / максимум - из диапазона датасета, для валидации.
Опциональные - можно оставить пустыми.
Дефолт любого параметра, участвующего в сравнении с ТТХ решений, -
worst-case: максимальный для массы грузовой единицы и нагрузки на пол
(робот должен поднять самый тяжёлый груз / не продавить пол),
минимальный для габаритов, проходов, высоты, шума, точности и доступной
мощности (робот должен пройти в самый узкий проход, вписаться в самый
низкий ярус, в самую тихую зону, в самое строгое требование по точности).
Согласовано с selection_algorithm.md §4.1 (таблица сравнения);
переименования и дефолты - §25, §26.

## 3. Единицы измерения характеристик решений

### Что
В конкурсной документации таблица характеристик не указывает единицы измерения.
Фиксируем сами.

### Значения
Единицы - как в `Датасеты_хакатон.xlsx`, для удобства сравнения характеристик решений с параметрами объектов:
- грузоподъёмность, масса - кг
- габариты - мм
- скорость - м/с
- производительность - операций/час
- автономность - ч
- точность позиционирования - мм
- мощность зарядки - кВт
- уровень шума - дБА
- срок службы - лет
- стоимость - руб.
- температура - °C
- ширина проходов, коридоров - м

### Источник
`Датасеты_хакатон.xlsx` (единицы параметров), конкурсная документация (таблица характеристик).

### Обоснование
Единая система единиц для характеристик решений и параметров объектов упрощает фильтрацию: сравнение идёт напрямую, без конвертации. Автоперевод при парсинге данных выполняется на стороне импорта.

### Влияние
Заполняется в `characteristic_type.unit`. При импорте из открытых источников - конвертация в единую систему.
Правило: при парсинге выполняется автоматический перевод единиц в целевую.

## 9. Кейсы решений

### Что
Конкурсная документация требует хранить «наличие реализованных кейсов».
В CSV у одного решения может быть несколько кейсов, и они повторяются между решениями.

### Значения
Отдельная таблица `solution_case` - многие-ко-многим.
Один кейс может относиться к нескольким решениям. Одно решение - несколько кейсов.

Поля: `id`, `name`, `description`, `source_url`, `source_date`.

### Источник
Конкурсная документация (поле «Кейсы» в CSV).

### Обоснование
Многие-ко-многим позволяет переиспользовать один кейс (например, «внедрение в X5 Group») для нескольких решений, если они развёрнуты в одном проекте.

### Влияние
`solution_case` + `solution_case_link (solution_id, case_id)`.

## 10. Нормализация данных

### Что
В CSV есть разнородность: ё/е, дефисы, опечатки, пробелы.

### Значения
Минимальная нормализация:
- буква «ё» → «е» (для поиска, не для отображения)
- дефисы и тире приводятся к обычному дефису
- trim пробелов
- удаление дублирующих пробелов

Состав карты автоправок:

| # | Поле                      | Ошибочная форма                                  | Каноническая форма                                | Где применяется                                                 |
|---|---------------------------|--------------------------------------------------|---------------------------------------------------|-----------------------------------------------------------------|
| 1 | Сценарий → process        | Доставка биоматериаловм                          | Доставка биоматериалов                            | normalizers/processes.py (TYPO_FIXES)                           |
| 2 | Подтип → solution_subtype | Робот уборщик                                    | Робот-уборщик                                     | mappers/catalog_mapper.py (SUBTYPE_TYPO_FIXES) + merge-шаг seed |
| 3 | Подтип → solution_subtype | Робот инвентаризатор                             | Робот-инвентаризатор                              | там же                                                          |
| 4 | Подтип → solution_subtype | Модульная наводная многофункциональная платформа | Модульная надводная многофункциональная платформа | там же                                                          |
| 5 | Подтип → solution_subtype | Роботизированный 3D принтер                      | Роботизированный 3D-принтер                       | там же                                                          |

Конкретные опечатки исправляются автоматически с фиксацией в этом файле и логом при работе seed.

### Источник
`catalog_export_v4.csv`, `Датасеты_хакатон.xlsx`.

### Обоснование
Нормализация нужна для консистентного поиска и фильтрации. Но данные из CSV могут содержать осмысленные различия (разные модификации) - не унифицируем жёстко. Объединение подтипов из карты - обосновано в §13.

### Влияние
Применяется в seed-скрипте. Карта автоправок обновляется по мере обнаружения.

## 12. Расхождение по applications (250 vs 256)

### Что
Разрез поля «Сценарий» по «, » даёт 250 уникальных применений (троек
«решение × отрасль × процесс»), а не 256. Принимается как финальное число.

### Значения
Принято: **250** `solution_application`. Без карты исключений разреза получилось бы 256:
лишние 6 строк - фрагменты названий, не являющихся самостоятельными процессами.

Карта исключений разреза (запятая внутри названия одного процесса,
`normalizers/processes.py`, SCENARIO_EXCEPTIONS) вынесена в открытые вопросы -
**§17, вопросы 1–2** (вместе с defensive-исключением, которое в v4 не встречается).

Расчёт: 250 + 4·(2−1) + 1·(3−1) = 256 без карты; 250 с картой.

### Источник
`catalog_export_v4.csv` (поле «Сценарий», 98 уникальных значений, сплошной просмотр),
data_model.md §5.3 (разрез по «, » с картой исключений).

### Обоснование
Фрагменты «труднодоступные районы», «патрулирование», «перевозка грузов» начинаются
со строчной буквы и не являются названиями процессов; разрез по ним порождал бы
мусорные строки справочника `process` и фантомные применения. README seed («Мониторинг, патрулирование, перевозка грузов» не разрезается)
фиксирует это правило для одного значения - зафиксировано и влияние на счётчик.

### Влияние
Счётчик приёмки `solution_application = 250`; процесс-справочник = 95 записей.
Seed по этому пункту не меняется. [вопрос закрыт - Q-1, Q-2](backlog/closed_questions.md).

## 13. Объединение подтипов

### Что
В CSV поле «Подтип» содержит четыре пары дублей - написания, отличающиеся
дефисом/пробелом или опечаткой. В `solution_subtype` они засеивались как разные
справочники, что ломало фильтрацию по подтипу.

### Значения
Четыре объединения (каноническая форма - с дефисом / без опечатки):

| Ошибочная форма                                  | Каноническая форма                                | Строк CSV (ошибочная) | Строк CSV (каноническая)                                      |
|--------------------------------------------------|---------------------------------------------------|-----------------------|---------------------------------------------------------------|
| Робот уборщик                                    | Робот-уборщик                                     | 4                     | 9                                                             |
| Робот инвентаризатор                             | Робот-инвентаризатор                              | 1                     | 1                                                             |
| Модульная наводная многофункциональная платформа | Модульная надводная многофункциональная платформа | 1                     | 1                                                             |
| Роботизированный 3D принтер                      | Роботизированный 3D-принтер                       | 1                     | 0 (форма есть только в маппинге §4 и уточнениях организатора) |

Итог: `solution_subtype` = 71 (68 CSV после объединения + 3 подтипа только из
маппинга §4: «Робот-тягач», «Мобильный манипулятор», «Интеллектуальный автобус»).
Каноническая форма «Роботизированный 3D-принтер» входит в 68 - строка CSV с формой
«3D принтер» (без дефиса) перенаправлена на неё.

### Источник
`catalog_export_v4.csv` (поле «Подтип»), уточнения организатора (морские роботы - надводные
платформы), карта автоправок §10.

### Обоснование
- «Робот-уборщик» и «Робот-инвентаризатор» - слитное/дефисное написание одного
  подтипа; в маппинге §4 и в текстах конкурсной документации используется дефисная форма.
- «наводная» - не слово; правильный термин для надводной платформы - «надводная»
  (подводная/надводная - пара из морской тематики уточнений организатора). Исходная форма в
  CSV - опечатка.
- «Роботизированный 3D принтер» (CSV, 1 строка) против «Роботизированный
  3D-принтер» (маппинг §4, уточнения организатора): то же слитное/дефисное написание;
  канонична дефисная форма по аналогии с первыми двумя парами.
- Дубли не несут семантики (не «разные модификации»): различие только в написании.

### Влияние
Seed: правка применяется в маппере до вставки (свежая БД получает только
канонические формы); отдельный merge-шаг (`dicts_repo.merge_solution_subtypes`)
чистит БД, засеянную до объединения (с дублями): перенаправляет `solution.solution_subtype_id`,
удаляет устаревшие записи `solution_type_subtype_mapping` и сами дубли. Выбрано
удаление, а не деактивация: у `solution_subtype` нет колонки `is_active`, а менять
схему нельзя; строки-дубли смысла не несут. Ссылки 7 решений CSV перенаправлены
на канонические подтипы (6 + 1 «3D принтер»). Лог: `solution_subtype: объединено
X пар, обновлено Y ссылок`.

## 21. Обязательные ТТХ решений

### Что
Уточнения организатора (обязательные ТТХ) требуют при подборе и фильтрации
«габариты, масса, точность позиционирования, требования к инфраструктуре».

### Значения
8 обязательных ТТХ (`is_required = true` в `characteristic_type`):
- payload_kg - грузоподъёмность, кг;
- mass_kg - масса, кг;
- length_mm, width_mm, height_mm - габариты, мм;
- positioning_accuracy_mm - точность позиционирования, мм;
- charging_power_kw - мощность зарядки, кВт (инфраструктурное требование);
- noise_level_dba - уровень шума, дБА (инфраструктурное ограничение объекта).

«Требования к инфраструктуре» покрыты charging_power_kw и noise_level_dba
(мощность зарядной инфраструктуры и акустика зон - уточнения организатора); требования
к покрытию/связи остаются текстовыми характеристиками (floor_coverage_req,
communication_req) без числовой фильтрации.

### Источник
Уточнения организатора (перечень обязательных ТТХ, инфраструктурные поля
датасетов), конкурсная документация (таблица характеристик).

### Обоснование
Габариты и масса - критерии геометрической совместимости (проезды, коридоры,
лифты); точность - пригодность к операции; зарядная мощность и шум -
инфраструктурные ограничения объекта (уточнения организатора). Без обязательности этих
полей фильтрация по обязательным ТТХ не работает.

### Влияние
`characteristic_type.is_required`; при отсутствии обязательного ТТХ решение
получает статус `needs_check` («требует проверки») с явным указанием
границ применимости (уточнения организатора). Seed проставляет флаги; тест -
`test_characteristics.py::test_flags`.

## 23. RaaS-модель («роботы как услуга»)

### Что
Сценарий RaaS обязателен (конкурсная документация; уточнения организатора: сравнение
не менее трёх сценариев). Логика расчёта формируется командой самостоятельно и
фиксируется здесь (уточнения организатора: «фиксирует все допущения по модели RaaS в
отдельном разделе решения»).

### Значения
- Модель платежей: фиксированная ставка за робота в месяц (`fixed`;
  economic_model.md 2.11). Плата за использование и смешанная модель -
  дополнительные режимы того же расчёта.
- Ставка RaaS: 1.5–3% от цены робота в месяц (при цене 5 млн руб. -
  75–150 тыс. руб./мес за робота).
- Срок контракта: 3 года (36 месяцев); допустимый диапазон ввода -
  1–10 лет (валидация каталога допущений, AssumptionService;
  диапазон зафиксирован здесь, дефолт 3 - выше).
- Выкуп: опциональный, по остаточной стоимости в конце контракта.
- CAPEX при RaaS: минимальный или 0 (без выкупа). При выкупе - остаточная
  стоимость учитывается в CAPEX года выкупа.
- Распределение затрат: платежи RaaS, электроэнергия, связь, персонал
  эксплуатации - OPEX; CAPEX - только инфраструктурные работы на стороне
  эксплуатанта (если требуются), амортизация оборудования остаётся у оператора
  услуги и в расчёт покупателя не входит.

### Источник
Уточнения организатора (структура платежей, срок контракта, выкуп, распределение
CAPEX/OPEX - на усмотрение команды), конкурсная документация (не менее трёх сценариев),
RaaS-сценарий обязателен; допускается упрощённая модель
платежей, но сценарий из сравнения не убирается.

### Обоснование
Фиксированная ставка - минимальная детерминированная модель, достаточная для
сравнения сценариев по единым показателям (уточнения организатора: CAPEX, OPEX, годовой
эффект, окупаемость, ROI). Диапазон ставки - типовые рыночные RaaS-контракты
(окупаемость парка оператора 3–4 года). Срок 3 года соответствует горизонту
окупаемости и даёт сопоставимость с покупкой по TCO.

### Влияние
Формулы - `docs/economic_model.md` §2.11: Payment_year = Fixed_rate × N_robots;
OPEX_year_raas = Payment_year + C_electricity + C_communication + C_staff;
CAPEX_raas = 0 (или остаточная стоимость в год выкупа). Параметры (ставка, срок,
выкуп) - изменяемые допущения расчёта в `calculation_assumption`.

## 26. Новые параметры: нагрузка на пол, шум, точность

### Что
Три новых параметра (нет в XLSX организатора, добавлены overrides-файлом).

### Значения

| Код                              | Название                                                                     | Типы  | Дефолт | Диапазон | Источник                                  |
|----------------------------------|------------------------------------------------------------------------------|-------|--------|----------|-------------------------------------------|
| floor_load_max_kg                | Максимальная нагрузка на пол (на точку опоры), кг                            | склад | 5000   | 500-5000 | уточнения организатора                    |
| max_allowed_noise_dba            | Максимально допустимый уровень шума (в самой тихой зоне), дБА                | все 3 | 25     | 25-80    | уточнения организатора                    |
| required_positioning_accuracy_mm | Требование к точности позиционирования (в самой требовательной операции), мм | все 3 | 1      | 1-50     | уточнения организатора (обязательные ТТХ) |

### Обоснование
- floor_load_max_kg - трактовка «на точку опоры, а не на м²»: у мобильного
  робота нагрузка передаётся через колёса/опоры, норматив полов даётся на
  точку опоры (СНиП полы); сравнение mass_kg <= floor_load_max в
  selection_algorithm.md §4.1 консервативно (масса робота целиком на одной
  точке - запас). Диапазон 500-5000 кг: нижняя граница - старые полы
  ремонтных цехов, верхняя - промышленный бетон с упрочнением (типовые
  значения для складских полов). Дефолт 5000 (верх) - правило «worst-case
  сверху»: параметр читается как паспортная ёмкость пола нового
  промышленного объекта (пол выдерживает ДО 5000 кг на точку); строгость
  сравнения обеспечивает консервативная трактовка массы робота, а при
  старых полах пользователь снижает значение (диапазон позволяет). Если
  на Q&A организатора закрепят иную семантику («дефолт = самый слабый
  пол», 500) - поменять одной строкой в parameter_overrides.json
  [вопрос закрыт - Q-13](backlog/closed_questions.md).
- max_allowed_noise_dba - 25 дБА - санитарная норма для палат (ночное время,
  СанПиН) и самых тихих зон; 80 дБА - предельно допустимое для
  производственных зон. Дефолт 25 - worst-case (самая тихая зона).
- required_positioning_accuracy_mm - 1 мм - самые строгие операции
  (манипуляции, лабораторная автоматика); 50 мм - грубая транспортировка.
  Дефолт 1 - worst-case (самая требовательная операция).

### Влияние
seed: 3 параметра (итого 135), 7 связей (итого 145). Параметры - необязательные
(дефолт есть всегда); используются подбором как эталоны сравнения.
