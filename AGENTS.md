## 1. Роли и стек проекта

### Роли
- Основная роль — Senior Fullstack Developer: оркестрация, принятие решений, финальный код, интеграция
- Субагенты:
    - explorer: read/grep/glob, возвращает file:line + вывод, без прав записи
    - verifier: изоляция, не наследует историю, проверяет с нулевым контекстом
    - executor: работает по готовому плану мастера, полные права в своей директории

### Стек
- Frontend: Next.js App Router, TypeScript, Tailwind
- Backend: Java 21, Spring Boot, Spring Data JPA, Spring Security
- БД: PostgreSQL
- Инфраструктура: Docker

## 2. Стиль и уровень кода

### Стиль
- Формат и именование — Google Java Format
- Язык интерфейса — полностью русский

### Уровень
- Расширяемый MVP для защиты на хакатоне и сдачи заказчику

## 3. Карта репозитория

### Зоны
- ./frontend — Next.js приложение
- ./backend — Spring Boot приложение
- ./docs — документация (состав — в разделе 4)
- ./data — файловые хранилища runtime (attachments, simulations, exports, admin-imports)
- ./scripts — seed, e2e-верификация
- docker-compose.yml — в корне репозитория
- ./scripts — импорт, seed, миграции, утилиты

### Backend
- Слои: controller → service → repository
- Подпакеты: /config, /domain, /dto, /mapper, /validation, /exception, /security
- Модули: /economics, /selection, /catalog, /import
- Миграции: src/main/resources/db/migration
- Тесты: src/test

### Frontend
- app/ — маршруты App Router
- components/ — переиспользуемые компоненты
- lib/ — клиенты API, утилиты, типы
- hooks/ — кастомные хуки

### Правила размещения
- Новый модуль — в соответствующую зону, не в корень
- Новая отрасль, объект, параметр — через справочники и админку, не хардкод
- Новый расчёт — в /economics
- Новый API — в /controller + обновить OpenAPI
- Новая миграция — в db/migration
- Новый компонент — в /components, если переиспользуемый
- Новое допущение — в docs/assumptions.md
- Новый термин — в docs/glossary.md
- Вопросы разработки и их закрытие — только в журнале
  docs/backlog/closed_questions.md; в остальных документах — максимум
  метка «[вопрос закрыт — Q-N]» со ссылкой
- Никаких упоминаний процесса разработки в комментариях кода и
  основном тексте docs (ревью/фикс/срез/задача N/коммит); хроника —
  только в worklog.md §6, история ограничений — architecture.md §11;
  пользовательские строки и Swagger-описания — без процессных меток

## 5. Домен и цели

- Платформа предынвестиционной оценки роботизации
- Не заменяет детальное проектирование; результат — гипотеза, требует верификации
- Целевая аудитория: руководители, технические директора, аналитики, логисты
- Базовые типы объектов: склад, аэропорт, медицинское учреждение
- Роли: гость, зарегистрированный пользователь, администратор (вендор — опционально)
- Приоритетный сценарий: экспресс-предынвестиционная оценка

## 6. Границы MVP

### Входит
- Каталог решений: иерархия, фильтры, поиск, сравнение
- Подбор решений с объяснением включения и исключения
- Экономика: CAPEX, OPEX, TCO, ROI, окупаемость, годовой эффект
- Три сценария: базовый + покупка + RaaS
- Чувствительность минимум к 3 параметрам
- 2D-визуализация объекта и KPI
- Экспорт PDF и Excel/CSV
- Админка: каталог, справочники, нормативы, источники

### Вне MVP
- Автоматический парсинг каталога
- Плановое автообновление каталога
- Интеграции с WMS, ERP, 1C, госреестрами
- 3D-визуализация
- ML и оптимизация

### Правило
- Функции вне MVP — только если не ломают основной путь и остаётся время
- Лучше узкий рабочий продукт, чем широкий сломанный

## 7. Архитектурные принципы

### Общее
- Разделение клиента и сервера: Next.js + Spring Boot + PostgreSQL
- BFF-паттерн: Next.js управляет сессией, Spring Boot валидирует JWT
- Демо не зависит от внешних источников: работает на заранее загруженных данных
- Расширяемость: новые отрасли, объекты, решения, расчёты — через справочники и админку, без правки ядра

### Backend
- Слои: controller → service → repository
- Бизнес-логика только в service, в контроллерах — приём и ответ
- Расчёты — в /economics, подбор — в /selection, каталог — в /catalog
- DTO для API, сущности JPA наружу не отдавать
- Транзакции на уровне service, валидация через Bean Validation
- Параметры объектов и характеристики решений — через метаданные, не хардкод

### Frontend
- App Router, Server Components по умолчанию
- 'use client' — только где действительно нужно
- Server Actions для мутаций внутри приложения
- Типы API — из OpenAPI, не писать руками
- Прямых вызовов Spring Boot нет, только через BFF

### Конфигурация и инфраструктура
- Конфигурация — через .env, секреты не в репозитории
- Docker + docker-compose, один `docker-compose up` поднимает всё
- СУБД — PostgreSQL, схема меняется только через миграции

### Детали
- Полное описание — в docs/architecture.md
- Модель данных — в docs/data_model.md
- Экономика — в docs/economic_model.md
- Подбор — в docs/selection_algorithm.md

## 8. Домен: экономика и подбор

### Экономика
- Формулы — только из docs/economic_model.md
- Свои коэффициенты и нормативы запрещены
- Показатели: количество роботов, CAPEX, OPEX, TCO, годовой эффект, окупаемость, ROI
- Амортизация CAPEX: метод и срок службы — в assumptions.md
- RaaS: структура платежей, распределение затрат, срок контракта — в assumptions.md
- Сценарии: базовый без роботизации + покупка + RaaS
- Чувствительность минимум к 3 параметрам
- Все формулы, единицы, источники — видны пользователю и в отчёте

### Подбор
- Логика — только из docs/selection_algorithm.md
- Иерархия: отрасль → тип объекта → процесс → тип решения → продукт
- Фильтрация по ТТХ и инфраструктурным ограничениям
- Критическое ограничение → решение исключено
- Нехватка данных → статус «требует проверки»
- Ранжирование объяснимое: критерии и вклад факторов видны пользователю
- Ручное добавление решения — с предупреждением и причиной

## 9. Безопасность и данные

### Безопасность
- Роли: гость, пользователь, админ; права разграничены
- Пароли только в хеше (argon2 или bcrypt)
- Изоляция проектов разных пользователей
- Передача данных по защищённому протоколу при размещении в сети
- Воспроизведение расчёта: хранить версию исходных данных и модели
- Логирование без чувствительных данных

### Данные
- Никаких реальных ПДн в демо-данных и seed-файлах
- Удаление проекта — вместе с загруженными файлами
- docs/source — исходные материалы организатора, только чтение
- data/attachments, data/simulations, data/exports, data/admin-imports —
  файловые хранилища runtime (создаются сервисами)
- data/exports — примеры выгрузок
- Цены в демо: с НДС, без доставки, пусконаладки и интеграции, если иное не указано организатором

### Перед задачей

- Если данных не хватает — задать вопрос, не додумывать

### Формат работы
1. План
2. Код
3. Тесты
4. Как проверить
5. Риски и допущения

### Git-правила

#### Источник истины
- Репозиторий: github.com/meyuugao/LCT_Hakaton.
- Ветка: main.
- PAT-токен: пустая строка — если не задан, работать с локальной копией
  без pull/push, но коммиты делать обязательно.

#### Перед каждым срезом
1. Синхронизировать проект: `git pull origin main`
   (при наличии PAT — через HTTPS URL с токеном).
2. Убедиться, что локальная копия не расходится с удалённой.

#### Формат сообщений коммитов
- Первая строка: `<тип>: <описание>` — одно осмысленное действие в
  повелительном наклонении («починить seed-сервис», «обновить worklog»).
- Разрешённые типы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`,
  `data`, `infra`.
- Язык описания: русский или английский — единообразно в рамках серии
  коммитов.
- Длина первой строки: до 72 символов.
- Запрещены в сообщении: символы `§`, `¶`, `‡`, `†`, HTML-сущности,
  экранированные кавычки, лишние точки и двоеточия в конце, многоточие
  вместо описания, Unicode-мусор, а также фрагменты вида «…ным §8»,
  «см. §11», `<...>` и обрывки предложений из документации.
- Уточнение при необходимости — второй строкой (body) после пустой
  строки: до 200 символов, без спецсимволов.
- Хеш коммита фиксируется в docs/worklog.md §6.
- Самопроверка перед каждым коммитом: формат соблюдён, запрещённых
  символов нет, первая строка не длиннее 72, описание осмысленное.

#### После каждого среза
1. Зафиксировать изменения: `git add -A`;
   `git commit -m "<тип>: <описание>"` — сообщение строго по формату выше.
2. Отправить в репозиторий: `git push origin main`
   (при наличии PAT — через HTTPS URL с токеном).
3. Зафиксировать хеш коммита в docs/worklog.md §6.

#### Правила срезов
- Вертикальный срез — сквозная функциональность от БД до frontend, плюс тесты.
- Не выходить за границы среза. Не начинать следующий.
- Перед срезом — git pull. После — commit + push.
- Если срез затрагивает схему БД — только через новую миграцию.
- Если срез затрагивает API — обновить OpenAPI.
- Если срез затрагивает решения проекта — обновить соответствующий документ
  в docs/* и добавить запись в docs/worklog.md.

#### Запреты
- Не коммитить секреты, креды, .env.
- Не коммитить артефакты сборки (build/, .next/, __pycache__/).
- Не редактировать применённые миграции.
- Не переписывать документы в docs/source/.
- Не переписывать историю git без явного запроса.

### После задачи
- Меняется API — обновить OpenAPI и сгенерировать клиент
- Меняется схема БД — миграция + обновить docs/data_model.md
- Появились допущения — записать в docs/assumptions.md
- Новый термин — добавить в docs/glossary.md
- Обновить релевантный профильный документ
